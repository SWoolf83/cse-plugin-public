# cse — Cascade Spec Engine plugin

The full Cascade Spec Engine toolset, packaged as **one versioned Claude Code plugin**.
This is the **single source of truth** for the CSE skills, the `cascade-api` MCP server,
and the capture hooks. Installed copies are *generated* from this directory — never
hand-edit `~/.claude/...` copies again.

## What's in the box

- **54 skills** under `cse/skills/<bare-name>/` — every command is colon-namespaced as `/cse:<name>`
  (e.g. `/cse:spec`, `/cse:receive`, `/cse:economics`). Colons are plugin-exclusive; that is the
  reason this is a plugin and not a pile of loose skills.
- **`cascade-api` MCP server** — **vendored** into the plugin at `cse/mcp/cascade-api/index.js`
  (a single self-contained esbuild bundle). `cse/.mcp.json` points at it via
  `${CLAUDE_PLUGIN_ROOT}/mcp/cascade-api/index.js`, so installing the plugin makes the `cascade_*`
  tools (`cascade_list_packages`, `cascade_pull_package`, `cascade_accept_package`, …) available
  with **no** separate `.mcp.json` wiring and **no** access to the repo.
- **Vendored skill registry** — `cse/mcp/cascade-api/skill-registry.json`, generated from the
  SKILL.md frontmatters on every build. The deferred `cascade_find_skill` MCP tool searches it for
  just-in-time skill discovery (see *Lean skill loading* below).
- **Capture hooks** — **vendored** into the plugin at `cse/hooks/scripts/*.js` (one self-contained
  esbuild bundle per hook). `cse/hooks/hooks.json` points at them via
  `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/<hook>.js`. These mirror what `scripts/install-hooks.js` used
  to write into `~/.claude/settings.json` (decision / knowledge / work capture). Installing this
  plugin **supersedes** the manual hook install (see below).
- **Standalone hooks** — a few hooks ship as **hand-written self-contained ESM** directly in
  `cse/hooks/*.mjs` (pure Node stdlib, **no** build step): `chief-trigger.mjs` (Chief-of-Staff nudge)
  and `memory-preserve.mjs` (memory preservation — see below). These live alongside `hooks/scripts/`
  but are **not** regenerated by `npm run build:cse-plugin` (which only rebuilds `hooks/scripts/*.js`),
  so edits to them survive a rebuild.

## Memory preservation (offload before compaction)

Claude Code project memory lives at `~/.claude/projects/<project-slug>/memory/MEMORY.md` and is loaded
into context each session — but content beyond Claude Code's ~24KB read-limit is **silently dropped**.
When the index grows past that, compacting it (an Edit/Write that shrinks the file) would lose the
overflow forever. The **`memory-preserve` PreToolUse hook** (`cse/hooks/memory-preserve.mjs`) closes
that gap: it intercepts the **first** over-threshold compaction edit, auto-writes a verbatim local
archive copy, **blocks** the edit with an agent-readable reason, and instructs the agent to push the
content to a single versioned Cascade artifact (`cascade memory-snapshot <archive>`) and compact down
to a low watermark before retrying.

It pairs with `cascade_handoff` (restart continuity): handoff carries the *thread*, memory-preserve
carries the *durable index*.

### The four anti-thrash guards (+ rate floor)

A naive "snapshot when big" trigger would write a snapshot almost every session once the file hovers
near the limit. Four guards engineer that out:

1. **Edit-coupled trigger** — preservation only fires when an `Edit`/`Write`/`MultiEdit` targets a
   `MEMORY.md` that is over the **HIGH** watermark. Reads, other files, and under-threshold edits are
   strict no-ops.
2. **Content-hash dedup** — the current `MEMORY.md` content is SHA-256'd; if it matches the
   last-preserved hash, nothing is re-archived or re-pushed (the retried compaction edit is *allowed*
   because its pre-edit content was already preserved).
3. **Single versioned artifact** — there is **one** standing Cascade `memory-snapshot` artifact whose
   id is persisted in the state sidecar and reused across sessions. Each changed preservation appends
   a new **version** — never a new artifact.
4. **Hysteresis band** — the block message instructs compaction down to the **LOW** watermark, well
   below HIGH, so a freshly compacted file has ample headroom and won't re-trigger for many sessions.
   If compaction can't reach LOW, the agent is told to say so explicitly rather than silently re-loop.

Plus a **24h rate floor**: regardless of edits, at most one preservation per ~24h (tracked via the
last-preserved timestamp). Inside the window, an over-threshold edit is allowed without re-archiving.

### What is automatic vs. what the agent does (hybrid)

- **The hook does automatically:** detect the over-threshold compaction, write the verbatim
  `_archive/MEMORY-snapshot-<YYYY-MM-DD>.md`, record state (hash + timestamp), and block with
  instructions.
- **The agent does (one step):** run `cascade memory-snapshot <archive-path>` to create-or-update the
  single versioned Cascade artifact, then compact `MEMORY.md` to ≤ LOW and retry the edit.

### `cascade memory-snapshot <file>`

Create-or-update the single standing snapshot artifact from `<file>` (the live `MEMORY.md` or one of
its `_archive/MEMORY-snapshot-*.md` copies). Idempotent and content-hash-aware:

- **Unchanged content** → prints `unchanged, skipped`, no new version.
- **Changed content** → reuses the artifact id from the state sidecar and appends a new **version**
  (or creates the artifact on first run and records its id).
- **Offline / no creds / artifact storage unavailable** → still records local state (so the hook stops
  re-blocking) and warns that the artifact push is **deferred**; re-run when authenticated to push.

### Config reference

All watermarks/thresholds have sane defaults and are env-overridable (resolved in
`cse/hooks/memory-preserve-core.mjs`). The memory dir + `_archive/` + state sidecar are **derived from
the edited file path** — no per-machine absolute path is hardcoded.

| Setting | Env var | Default |
| --- | --- | --- |
| HIGH watermark (trigger) | `CASCADE_MEMORY_HIGH_BYTES` | `22528` (~22 KB) |
| LOW watermark (compact target) | `CASCADE_MEMORY_LOW_BYTES` | `16384` (16 KB) |
| Rate floor (hours) | `CASCADE_MEMORY_RATE_FLOOR_HOURS` | `24` |

**Layout** (derived from `…/memory/MEMORY.md`):

- `…/memory/_archive/MEMORY-snapshot-<YYYY-MM-DD>.md` — verbatim local snapshot.
- `…/memory/_archive/.preserve-state.json` — `{ artifactId, lastArchivedHash, lastPushedHash, lastPreservedAt, lastVersionNo }`. Two hashes by design: `lastArchivedHash` is hook-owned (retry-allow + dedup); `lastPushedHash` is CLI-owned (push dedup) and set only after a successful artifact push — keeping them separate is what prevents the hook's recorded hash from skipping the CLI push.

**Lean-MEMORY.md breadcrumb convention:** after compacting, leave a one-line pointer at the top of
`MEMORY.md` to the snapshot artifact id + the local `_archive/` path, so a future session knows where
the full history lives.

### Ship steps

The hook ships via the cse plugin like everything else:

```bash
npm run build:cse-plugin        # re-vendor (leaves the standalone .mjs hooks intact)
node scripts/check-plugin-drift.mjs
# bump the cse plugin version + publish:
/cse:release
# then RESTART the Claude Code session so the new PreToolUse hook loads.
```

Tests: `node --test cse/hooks/__tests__/memory-preserve.test.mjs`.

## Install (local marketplace)

From the repo root:

```bash
# 1. Register this repo as a local marketplace (one-time; declared in user settings)
claude plugin marketplace add /path/to/cascade   # the repo root, which holds .claude-plugin/marketplace.json

# 2. Install the plugin
claude plugin install cse@cascade-hq

# 3. (optional) Inspect what got installed
claude plugin details cse
```

Or load it directly without a marketplace for a quick test:

```bash
claude --plugin-dir /path/to/cascade/cse
```

After install, `/cse:spec`, `/cse:receive`, `/cse:economics`, and the other 43 commands resolve,
and the `cascade_*` MCP tools are callable — including from a marketplace install (no repo access
required).

## Install (delegated / remote user)

The monorepo is **private**, so a delegated or remote user cannot `marketplace add` it. Instead they
add the dedicated, distributable mirror repo **`SWoolf83/cse-plugin`** (a byte-identical mirror of
`cse/` plus a root `marketplace.json`):

```bash
# 1. Add the distributable marketplace (requires access to the dist repo)
claude plugin marketplace add SWoolf83/cse-plugin

# 2. Install the plugin (the marketplace name stays 'cascade-hq')
claude plugin install cse@cascade-hq
```

This yields the same self-contained install: all 51 `/cse:*` commands resolve and the `cascade_*`
MCP tools are callable, with **no monorepo access required**.

> **Runtime auth (not solved here).** The `cascade-api` MCP server authenticates **per user at
> runtime** — after installing, run `cascade login` (the Cascade CLI) so the MCP tools can make
> authenticated Supabase calls on your behalf. This packaging ships the plugin only; it does **not**
> provision credentials. Each user supplies their own login.

### Self-contained MCP + hooks (dq-2: vendored into the plugin)

Decision **dq-2 = vendor**: the MCP server and the capture hooks are **bundled into the `cse/`
subtree** so a marketplace install — which copies *only* `cse/` into
`~/.claude/plugins/cache/<marketplace>/cse/<version>/` — is fully self-contained. There is **no**
dependency on `${CLAUDE_PLUGIN_ROOT}/../harnesses` or `${CLAUDE_PLUGIN_ROOT}/../dist`, and **no**
repo `node_modules` is required at runtime.

- MCP: `cse/mcp/cascade-api/index.js` — a single esbuild bundle of
  `harnesses/mcp-servers/cascade-api/src/index.ts` with all runtime deps
  (`@modelcontextprotocol/sdk`, `@supabase/supabase-js`, `zod`) **inlined** (~1.5 MB, one file, no
  `node_modules`). `cse/.mcp.json` → `${CLAUDE_PLUGIN_ROOT}/mcp/cascade-api/index.js`.
- Hooks: `cse/hooks/scripts/<hook>.js` — one esbuild bundle per hook from `src/daemon/hooks/*.ts`.
  `cse/hooks/hooks.json` → `${CLAUDE_PLUGIN_ROOT}/hooks/scripts/<hook>.js`.

**How the vendoring works.** The bundles are generated by an npm script:

```bash
npm run build:cse-plugin   # runs scripts/build-cse-plugin.mjs (esbuild --bundle, platform=node, format=esm)
```

This is **packaging only** — it does not change MCP tool behavior or hook behavior.

**When to re-run it.** Only when the MCP source (`harnesses/mcp-servers/cascade-api/src/`) or the
hook source (`src/daemon/hooks/*.ts`) changes. After re-vendoring, bump
`cse/.claude-plugin/plugin.json` `version` and reinstall (`claude plugin update cse@cascade-hq`) so
the cache snapshot refreshes. The **drift guard enforces freshness** (see below), so a stale vendor
fails CI / pre-flight rather than silently shipping.

## Lean skill loading / context economy

A large skill set has a recurring, always-on cost. Per the Claude Code docs, **every installed
skill's `description` is always in context** (the skill *body* only loads when the skill is
invoked). With 54 skills, the cse descriptions are the always-loaded cost — so we keep that cost
small and **bounded** without ever reducing a skill's invocability.

Three levers (all applied here):

1. **Trim descriptions (the always-loaded cost).** Every `description` is a tight, **trigger-first**
   one-liner — `Use when you want to X …` — capped at **140 chars** and enforced by the drift lint
   (below). This roughly **halved** the total description char-sum. Any nuance lost to the trim is
   carried in an optional **`when_to_use:`** frontmatter line, which does **not** load into
   always-on context — it feeds the registry / `cascade_find_skill` (next lever).

2. **`cascade_find_skill` — deferred JIT discovery.** MCP tools are natively **deferred** (surfaced
   via ToolSearch), so `cascade_find_skill` adds **~0 always-loaded cost** — its schema only loads
   once it's searched for. It does a static keyword search over a **vendored**
   `skill-registry.json` (name + description + `when_to_use`) and returns the best-matching skill(s)
   with how to invoke them (`/cse:<name>`). This is the discovery path that covers **name-only**
   skills (lever 3) — Claude can still find and run a skill even when you've trimmed its description
   out of always-on context. The registry is regenerated + vendored on every `npm run build:cse-plugin`
   (drift-guarded for sync), so it never goes stale.

   ```text
   cascade_find_skill({ query: "pull a youtube transcript into a knowledge package" })
   → { matches: [ { name: "ingest", command: "/cse:ingest", when_to_use: "…", invoke: "Run /cse:ingest …" } ] }
   ```

3. **`skillOverrides` tiering (opt-in, user settings).** You can trim the always-loaded cost
   **further** by tiering skills in your *own* `settings.json`. This is **guidance + a sample** — we
   never set it for you, and we never add `disable-model-invocation` / `user-invocable: false` to any
   skill (those would stop Claude from invoking it). All cse skills stay Claude-invocable; tiering
   only changes how much of each skill is *always loaded*, and `cascade_find_skill` recovers any
   skill you push to name-only.

   - **Tier 1 — core (full description always loaded):** the skills you reach for constantly
     (e.g. `spec`, `gate`, `qa`, `capture`, `decide`, `log`).
   - **Tier 2 — reference (name-only):** useful but occasional — keep the name in context, drop the
     description; rediscover via `cascade_find_skill`.
   - **Tier 3 — rare (off):** skills you essentially never use; turn them off and re-enable when
     needed.

   Sample `skillOverrides` to copy into your `~/.claude/settings.json` (adjust to taste):

   ```jsonc
   {
     "skillOverrides": {
       // Tier 2 — name-only (description dropped from always-on context; find via cascade_find_skill)
       "cse:archaeology":         { "loading": "name-only" },
       "cse:project-archaeology": { "loading": "name-only" },
       "cse:backfill":            { "loading": "name-only" },
       "cse:meeting-sync":        { "loading": "name-only" },
       "cse:prd":                 { "loading": "name-only" },
       "cse:economics":           { "loading": "name-only" },

       // Tier 3 — off (re-enable when you need them)
       "cse:release":             { "enabled": false }
     }
   }
   ```

   > The override key names mirror your installed skill identifiers; confirm the exact keys with
   > `claude plugin inspect cse@cascade-hq`. The schema is owned by Claude Code, not by this plugin —
   > this is recommended guidance you opt into, not a change the plugin makes.

**Guardrail.** `scripts/check-plugin-drift.mjs` **fails** if any description exceeds the 140-char
cap (so the always-loaded cost can't regress) or if the vendored registry drifts from the skills
(so JIT discovery can't go stale). Both run in `--vendor-only` mode (no install required).

## Releasing (`/cse:release`)

To publish a new version to the distributable mirror repo (`SWoolf83/cse-plugin`), run the
`/cse:release` skill (or the npm script). It is a deterministic, gated flow — **nothing is pushed or
tagged if any gate fails**:

```bash
/cse:release patch          # in Claude Code (default bump is patch)
# or, non-skill parity:
npm run release:cse-plugin -- patch     # patch | minor | major
```

Steps, in order:

1. `npm run build:cse-plugin` — re-vendor the MCP + hooks from source.
2. `node scripts/check-plugin-drift.mjs` — the everyday **2-way, offline** guard (vendor fresh +
   install in sync).
3. Bump `cse/.claude-plugin/plugin.json` `version` per the `[patch|minor|major]` arg (default
   **patch**).
4. Clone the dist repo, sync `marketplace.json` + a byte-identical `cse/` mirror, commit, push to
   `main`, and tag `v<new-version>`.
5. **Post-push self-verify** — re-clone the pushed tag and byte-compare the pushed `cse/` against the
   local `cse/`; any mismatch fails the release.

Steps 1–3 are **pre-push gates**. The dist-repo freshness check is the orchestrator's post-push
self-verify (step 5) — deliberately **not** in `check-plugin-drift.mjs`, so the everyday guard stays
2-way and offline. The dist repo stays **private**; flipping it public is a manual step.

## Decommission the old delivery path

The old flow hand-copied ~40 `$HOME/.claude/skills/cascade-*` directories (via
`scripts/install-hooks.js` and `cascade portfolio sync`). Those copies are now **stale and
superseded** by this plugin. To decommission:

```bash
# Remove the old hand-copied skill dirs (back them up first if you hand-edited any)
rm -rf "$HOME/.claude/skills/cascade-"*

# Remove the old manually-installed capture hooks from ~/.claude/settings.json.
# (The plugin now owns these. Leaving both installed makes hooks fire twice.)
# Edit ~/.claude/settings.json and delete the `hooks` entries whose command paths
# point at dist/daemon/hooks/*.js or ~/.claude/hooks/cascade/*.js.
```

`cascade portfolio sync` and `CLAUDE.md` have been updated to point at this plugin instead of
copying skills.

## Drift guard

The repo plugin must not silently diverge from what is installed. Run:

```bash
node scripts/check-plugin-drift.mjs              # both checks below
node scripts/check-plugin-drift.mjs --vendor-only  # freshness only (no install needed)
```

It enforces these and exits non-zero on any mismatch:

1. **Description-length lint (lean skill loading).** Fails if **any** `cse/skills/*/SKILL.md`
   `description` exceeds the **140-char cap** — so the always-loaded cost (see *Lean skill loading*
   above) can't silently regress as skills are added. Runs in `--vendor-only` mode too (no install
   needed).
2. **Registry sync (lean skill loading).** Fails if the vendored `cse/mcp/cascade-api/skill-registry.json`
   doesn't match a **fresh generation** from the current SKILL.md frontmatters (`scripts/gen-skill-registry.mjs`),
   so a stale registry can't ship. Regenerate with `npm run build:cse-plugin`.
3. **Vendor freshness (dq-2).** Re-bundles the MCP + hook sources into a scratch dir and
   byte-compares against the committed `cse/mcp/cascade-api/index.js` and `cse/hooks/scripts/*.js`.
   If a source changed but `npm run build:cse-plugin` was not re-run, the committed (and therefore
   installed) vendor is stale and the check fails. This is critical because the vendored files
   **are** the marketplace-install payload.
4. **Install sync.** Compares the installed `cse` snapshot against this repo source file-by-file
   (SHA-256) plus a `plugin.json` version check, catching a hand-edited install or a forgotten
   reinstall. The vendored tree is part of `cse/`, so a stale *committed* vendor is caught here too.

## Scope of this packaging

Pure relocation / path-rewrite / naming / packaging. Skill **behavior** is unchanged — no skill
logic was rewritten, no MCP tool behavior changed, and nothing was published to a remote marketplace.
